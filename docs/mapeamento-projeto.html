O que este agente é

Recebe ECD, ECF, NF-e/NFC-e, NFS-e, SPED Fiscal (EFD ICMS/IPI), SPED Contribuições e DIMP já validados em estrutura por agentes de origem. Cruza os fatos econômicos entre essas obrigações com um catálogo de regras e devolve um laudo técnico (achados determinísticos + parecer) para o time de tax compliance revisar. Não certifica regularidade e não aplica multa.

Papel no ecossistema

A complementaridade é o núcleo: o mesmo fato (venda, crédito, saldo, retenção) deve aparecer onde o leiaute oficial exige, com a mesma chave e o mesmo valor (ou a soma correta). Descendo a cadeia, falta é omissão; subindo, valor sem documento é falta de lastro.

Agentes de origem outros agentes

Leem XML/SPED brutos. Validam layout, PVA e regras internas (INT-*). Entregam JSON normalizado + relatório de validação (APROVADO / erros).

Falha estrutural não chega aqui como cruzamento: vira pré-condição não atendida.

Agente de parecer este repositório

Não relê arquivo original nem refaz PVA. Aplica PRE-001 a PRE-005, depois o motor de cruzamento. LLM só explica achados já produzidos.

Sem insumo: ausência de evidências — nunca omissão presumida.

Lote com todas as obrigações vs 2–3

O contrato e o motor já tratam lote incompleto. Não é obrigatório enviar as sete obrigações. O JSON exige obrigacoes com mínimo 1 item (contracts/entrada/lote.v1.schema.json); o teto é Entrada:MaximoObrigacoesPorLote = 500. Faltar ECD, DIMP ou NFS-e não rejeita o lote: cada obrigação entra em resultado.cobertura / aptidao.

Não há flag “modo lote completo vs parcial”. A diferenciação é por regra, conforme o que veio no JSON. Falta de insumo nunca vira omissão do contribuinte: vira AUSENCIA_EVIDENCIAS e revisão humana. Código: MotorRegras.ExecutarRegra.

Decisão da regraQuandoEfeito no status
NaoAplicavelNenhuma obrigação da regra está no lote (ex.: regra M1 num lote só de ECD+ECF)Se nenhuma regra de cruzamento executar → INCONCLUSIVA

Modelo de regra

O LLM não inventa regra. Catálogo JSON é dado versionado. Tipos de relação (vocabulário do NÚCLEO-1):

TipoSignificado para o cruzamento
PRE_DIRETAExiste em A ⇒ deve existir em B (falta = omissão)
PRE_REVERSAExiste em B ⇒ deve ter origem em A (falta = sem lastro)
IDTMesmo fato, mesmo valor na chave de junção
AGRSoma de vários registros = um valor no destino
LIMUm lado não pode exceder o outro (ex.: crédito ≤ destacado)
CNTSaldo final do mês t = saldo inicial t+1
PARCompatibilidade de regime / parâmetros
EXCExclusividade legítima — filtro antes da PRE
ESTRUTURA_GRAVE ESCRITURACAO_GRAVE ALERTA INFO evidência PVA / MANUAL / NORMA / DERIVADA

Regra DERIVADA não conclui irregularidade sozinha: o parecer lista hipóteses legítimas. Achados do motor: PRE_CONDICAO_NAO_ATENDIDA, INCONSISTENCIA_CRUZAMENTO, AUSENCIA_EVIDENCIAS, FALHA_TECNICA.

O que o laudo entrega ao tax compliance

Saída em duas camadas: resultado determinístico (sempre) e parecer LLM (se habilitado). Status possíveis: CONCLUIDA, CONCLUIDA_PARCIAL, INCONCLUSIVA, FALHA_TECNICA — nenhum significa “empresa regular”.

O sistema decide

Aptidão por obrigação, achados com regraId, valores dos dois lados, hipóteses legítimas, escopo/limitações, se revisão humana é obrigatória.

O LLM redige

Narrativa técnica citando trechos RAG. Não cria achado, não muda severidade, não cita multa/fraude, não determina providência ao contribuinte — só o que o analista deve revisar.

Ações para o time (por desenho)

Confirmar hipóteses legítimas, completar obrigação/período faltante, corrigir escrituração ou documento apontado pelo achado, tratar AUSENCIA_EVIDENCIAS como lacuna de cobertura — não como culpa. O prompt v1.1.0 proíbe o modelo de prescrever sanção ou obrigação de retificar.

Papel do LLM (e por que não está ativado)

O cruzamento não é feito pelo LLM. Ordem em AnalisesController: motor determinístico → fundamentação RAG por regraId → parecer LLM (só se habilitado).

PodeNão pode
Explicar achados já gerados; citar trechos (trechoId); pedir trechos extras via ferramenta base_conhecimento-consultar (máx. 3); redigir o JSON do contrato de parecer. Criar, apagar ou reclassificar achados; decidir conformidade; usar a RAG para “refazer” o cruzamento dos dados; aplicar multa ou mandar retificar.

Prompt: prompts/parecer/v1.1.0.md. Plugin: PluginBaseConhecimento.

Desligado por configuração

Parecer:Habilitado = false em src/Api.Agente/appsettings.json. Development só liga o Swagger. Sem OpenAI:ApiKey + ConnectionStrings:Agente, o Program.cs nem registra o chat. A API ainda devolve o motor com a limitação: “Parecer por LLM desabilitado; retornados apenas os resultados determinísticos.”

A fundamentação RAG (ServicoFundamentacao) independe do LLM: consulta MCP consultar_base_conhecimento por cada achado (exceto PRE-*). Hoje também não fala com banco: BaseConhecimento:Endpoint e TokenAcesso vazios → “base não configurada”.

A ideia “LLM consulta a RAG com as regras para análise” está parcialmente no desenho: a RAG fundamenta e o LLM pode consultar de novo. Quem analisa o cruzamento dos dados é o motor, não o modelo.

São dois Postgres. Nenhum tem connection string versionada (senha via ambiente). Não há banco de obrigações: o lote entra no POST e não é persistido.

Passos para ter RAG local

$env:RAG_POSTGRES_PASSWORD = '<senha>'
docker compose -f docker-compose.rag.yml up -d
$env:ConnectionStrings__Rag = "Host=localhost;Port=5433;Database=rag;Username=rag;Password=$env:RAG_POSTGRES_PASSWORD"
  1. Subir a Api.RAG (Development: http://localhost:5203).
  2. Ingerir a base de estudo: definir RAG_TOKEN_ADMIN (papel rag.admin) e executar scripts/ingerir-base-regras.ps1 -ApiRag http://localhost:5203.
  3. No Agente, apontar BaseConhecimento:Endpoint para a URL do /mcp da RAG e BaseConhecimento:TokenAcesso com JWT de papel rag.consulta.
  4. Só então a fundamentação (e o LLM, se ligado) enxergam as regras na base.

Para ligar o parecer em Development, além da RAG: Parecer:Habilitado=true, OpenAI:ApiKey e ConnectionStrings:Agente (Postgres de consumo). Sem isso o chat nem é registrado.
